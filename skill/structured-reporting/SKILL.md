# 结构化汇报

基于《金字塔原理》（芭芭拉·明托）的核心方法，加上向上汇报的数字纪律。

## 开工前先问三个问题

不问清楚不要动笔。

1. **谁听？** 他已经知道什么、最关心什么、能做什么决定
2. **听完要他做什么？** 批准、给资源、知悉、还是拍板某个选择
3. **一句话结论是什么？** 写不出这一句，说明还没想清楚，先想

第 3 个问题的答案就是整份材料的塔尖。写不出来就不要往下写。

## 四条硬规则

### 1. 结论先行

先说结论，再说支撑。不要按时间顺序讲「我们先做了 A，然后做了 B，所以得出 C」——领导没耐心听完。

错：`本季度我们完成了需求梳理、开发、测试三个阶段，目前平台已上线。`
对：`平台已如期上线，三个模块全部交付。`

### 2. 标题写观点，不写主题

每个章节、每一页的标题，必须是一个**可以被反驳的判断**，不是一个名词短语。

| 主题（弱） | 观点（强） |
|---|---|
| 项目进展 | 三个模块全部如期上线 |
| 存在的问题 | 问题集中在抓取准确性，已定位根因 |
| 下一步计划 | 需要业务方 9 月底启动首个真实项目 |

检验方法：把所有标题单独拎出来连读一遍，如果能读成一段完整的论证，结构就对了。

### 3. 纵向是「为什么」，横向是 MECE

- **纵向**：上一层的每个论点，都由下一层回答「为什么这么说」
- **横向**：同一层的几个论点，相互独立、完全穷尽（MECE）

横向分组只有两种合法关系：**并列**（三个板块）或**递进**（发现问题→定位根因→给出方案）。混在一起就是结构乱了。

常见的 MECE 破坏：分类标准不统一。比如把「Beta 板块、竞品板块、海外链路」并列——前两个按模块分，第三个按地域分，读的人会困惑。

### 4. 开场用 SCQA

- **S 情境**：对方认可的事实
- **C 冲突**：打破情境的变化或问题
- **Q 疑问**：由冲突自然引出的问题
- **A 回答**：你的结论，也是全篇塔尖

例：
> 用研的测试用户、访谈资料、竞品情报过去分散在各人的表格里（S），跨项目查询困难、过程无法追溯（C），能不能把这三条链路收进同一个系统（Q）——一期已经做到了，三个模块全部上线（A）。

开场超过三句话还没到 A，说明啰嗦了。

## 数字纪律

汇报里的每个数字都会被追问，提前把口径准备好。

- 每个关键数字标明**口径与来源**
- 效率提升类数字必须注明是**实测**还是**主观评估**——两者不能混用
- 没有真实数据时写「暂无」或用能力对比代替，**禁止估算、禁止套用行业均值**
- 分不清是「计划 vs 实际」还是「原始计划 vs 调整后计划」时，先说清楚基准是哪个

如果被追问某个数字算不出来，正确答复是「这个数据要等 X 之后才有，到时候我带真实数字回来」，不是现场编一个。

## 成果措辞

描述已完成的工作，只用这些动词：已开发、已测试、已上线、已交付、已验证、已记录。

不要用「基本完成」「初步实现」「已具备能力」——这些词在汇报里会被理解为「没做完」。

## 范围纪律

汇报一个阶段的成果时，**下一阶段的内容不进「我们做了什么」**。

- 下期的需求文档、原型、排期甘特都不算本期成果
- 下期只在末尾单独一节出现，一行一条，不展开、不承诺日期
- 承诺了日期就等于立了军令状，除非你确定能兑现

## 交付前自查

逐条过，任何一条不过就回去改：

- [ ] 第一页（或第一段）就给出了结论
- [ ] 所有标题连读能成一段论证
- [ ] 每组论点是纯并列或纯递进，没有混用
- [ ] 同一层的分类标准统一
- [ ] 每个数字都能说清口径与来源
- [ ] 没有「基本」「初步」这类模糊措辞
- [ ] 下阶段内容没有混进本阶段成果
- [ ] 被问「所以呢」时，每一页都答得上来

## 检查已有文档时

如果用户给的是已经写好的材料，按以下顺序挑问题，先说结构再说细节：

1. 塔尖在哪？找不到就是最大的问题
2. 标题是主题还是观点？逐条列出要改的
3. 有没有 MECE 破坏？指出具体是哪几项分类标准不统一
4. 哪些数字缺口径？
5. 哪些措辞会被挑战？

每条问题给出**具体的改法**，不要只说「这里不够清晰」。
